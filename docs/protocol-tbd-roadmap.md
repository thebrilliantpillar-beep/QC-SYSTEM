### TBD-0002 — Record·Message ID 형식

### TBD-0003 — 타임스탬프·직렬화 형식

**우선순위: 낮음 · 사용자결정: 불필요(NO)**

1. **확정된 사실** — `qms_audit.py:25` `now()` = UTC ISO8601, 초 단위(마이크로초 절삭), "Z" 접미사. `qms_audit.py:26` `canonical()` = `sort_keys=True`, 구분자 `(",",":")`인 압축 JSON — 저장·미러링뿐 아니라 해시체인 계산에도 이 canonical 형태를 그대로 사용(무결성의 실제 기반).
2. **진짜 미정인 부분** — 이 형식을 프로토콜 전역표준으로 못박을지. 초단위 절삭이라 같은 초에 여러 이벤트가 생기면 타임스탬프만으로는 순서를 구분 못 함(현재는 문제 없음 — 이유는 TBD-0010 참고).
3. **QMS 운영 우선순위** — 낮음. 정렬은 timestamp가 아니라 SQLite seq+해시체인이 담당해서 이 절삭이 실제 사고로 이어진 적 없음.
4. **결정 성격** — 사용자 결정 불필요.
5. **선택지** — (a·권장) 현재 형식 + "정렬은 timestamp에 의존하지 말 것" 주의사항 기록. (b) 마이크로초까지 확장 — 지금 쓸모없는 변경. (c) 완전 미정 유지.
6. **권장안** — 현재 ISO8601(Z)+canonical 압축 JSON을 기록하되, "타임스탬프는 순서 보장에 쓰지 않는다"는 주의문을 같이 남긴다 — TBD-0010과 한 번에 처리.

### TBD-0005 — Record별 status enum·공통 lifecycle

**우선순위: 높음 · 사용자결정: 필요(YES) — ①묶음**

1. **확정된 사실** — `qms_audit.py:632,713-715` REQUEST lifecycle(ACKNOWLEDGED→IN_PROGRESS→RESULT→[VERIFIED→COMPLETED, PASS+VERIFIED일 때만])은 프로토콜 §5.1 제안과 정확히 일치하게 이미 구현됨. 대부분 Record는 `status="ACTIVE"` 기본값(§4.1 default)만 쓰고 그 외 전이는 없음. 워크플로우 TASK는 실제로 `IN_PROGRESS`/`PARTIAL`/`COMPLETED` 세 값만 씀(프로토콜이 제안한 PLANNED/READY/BLOCKED/WAITING_* 등은 아직 미사용, 모순은 아님).
2. **진짜 미정인 부분** — 이미 코드 안에 두 관행이 공존한다: 병합충돌용 ISSUE(`qms_audit.py:1097`)는 `status="OPEN"`(프로토콜 ISSUE enum과 일치), 반면 workflow 자동생성 ISSUE(`qms_audit.py:724-729`)는 `status="ACTIVE"`(프로토콜 ISSUE enum에 없는 값)이고, "해결됨" 여부는 status 변경이 아니라 연결된 STATE Record(`workflow_issue_is_active()`)로 판단한다 — 사실상 ISSUE 자체는 불변, 해결은 별도 STATE로 표현하는 방식. 이게 QMS의 의도된 설계인지, 아니면 두 코드 경로가 그냥 따로 발전해서 어긋난 것인지가 미정.
3. **QMS 운영 우선순위** — 높음. 가상의 미래 문제가 아니라 지금 코드에 이미 벌어진 불일치다. 다음에 또 다른 세션이 ISSUE를 만들면서 세 번째 관행(예: 실제로 status를 RESOLVED로 바꾸는 방식)을 추가하면 status 기준 검색·집계가 신뢰 불가능해진다.
4. **결정 성격** — 사용자 결정 필요 — 이번 로드맵에서 "지금 물어야 하는 결정"으로 분류.
5. **선택지** — (a·권장) append-only + STATE 해소로 통일: ISSUE는 절대 status를 바꾸지 않고, 해소는 항상 연결 STATE로 표현(현재 workflow 쪽 관행을 표준화). (b) status enum으로 통일: 프로토콜 제안대로 OPEN→...→RESOLVED/CLOSED로 직접 전이, STATE 메커니즘 폐기. (c) 이원 병행: status는 대략적 표시, STATE는 감사용 상세 — 단, 어느 쪽이 "진실"인지 명문화 필요.
6. **권장안** — append-only + STATE 기반 해소로 통일. 이 프로젝트가 이미 activity_log·protocol_adapters·AUDIT_EVENT 등 여러 곳에서 "감사 기록은 절대 수정하지 않는다"는 원칙을 지켜왔고(CLAUDE.md 3절), 이 방식이 그 철학과 가장 잘 맞는다. line 1097의 `status="OPEN"` 하나만 `"ACTIVE"`로 맞추면 코드 정합성도 회복된다.

### TBD-0007 — UPDATE_STATE 조건부 승인·GIT_COMMIT 정책 세부

**우선순위: 중상 · 사용자결정: 필요(YES) — ①묶음(DEPLOY 격차) + ②묶음(GIT_COMMIT 문서화)**

1. **확정된 사실** — **GIT_COMMIT**: `qms_audit.py:227-248,894-914` `git-commit-authorize`가 staged diff(`git diff --cached --raw --no-abbrev --root -z`)를 SHA-256으로 해시해 1회성 DECISION Record에 결속. pre-commit hook이 커밋 직전 manifest를 재계산해 actor·staged 내용·1회사용 여부까지 대조(`secrets.compare_digest`). post-commit이 커밋 생성 확인 후에만 소비. 이번 세션에서 실제 커밋 2건(9cef5ff 등)으로 end-to-end 검증됨. **UPDATE_STATE**: STATE Record는 workflow 실행 중 자동 생성되고, 그 워크플로우 자체의 task/run/token 인가 외에 별도의 UPDATE_STATE 전용 승인 게이트는 없다 — "조건부"의 실체는 "이미 인가된 workflow 실행 중"이라는 뜻으로 코드가 동작하고 있을 뿐, 문서화된 적은 없다.
2. **진짜 미정인 부분** — GIT_COMMIT의 manifest-binding 방식을 다른 EXECUTE 행위(특히 DEPLOY)에도 일반화할지. 지금 DEPLOY 승인은 단일 DECISION Record뿐이라 GIT_COMMIT보다 보증 수준이 약하다(이번 조사에서 새로 발견한 격차) — 실제로 이번 세션의 "coverage_limits commit → push → 배포" 작업에서 push/배포 자체는 이 manifest 결속 없이 진행됐다.
3. **QMS 운영 우선순위** — GIT_COMMIT 문서화는 중간(동작은 이미 완성, 프로토콜 문서만 안 따라감). DEPLOY 보강 여부는 중상 — 지금 사고가 난 적은 없지만, "커밋보다 배포 승인이 더 허술하다"는 비대칭은 방치할수록 어색해진다.
4. **결정 성격** — 사용자 결정 필요. GIT_COMMIT 문서화는 기술 제안으로 먼저 가능하지만, DEPLOY 보강 여부(리스크 수용 vs 강화 비용)는 사용자 판단이 필요하다.
5. **선택지** — (a) GIT_COMMIT 전용 문서화만: DEPLOY는 그대로 — 지금 비용 0, 비대칭은 남음. (b·권장·단계적) GIT_COMMIT 문서화 + DEPLOY는 백로그: 지금 당장 안 고치되 격차를 명시적으로 기록해 다음에 잊히지 않게. (c) DEPLOY도 즉시 manifest-binding 확장: 가장 안전하지만 새 코드·새 테스트 필요, 이번 스코프(조사·계획만) 밖.
6. **권장안** — GIT_COMMIT 부분은 지금 바로 문서화(이미 사실이라 비용 없음), DEPLOY 강화 여부는 사용자에게 리스크 수용 여부를 직접 묻는다 — "지금 강화할지, 알고 있는 채로 백로그에 남길지"는 QMS 배포 빈도·중요도에 대한 사용자의 감각이 필요한 판단이라 기술적으로 대신 결정하지 않는다.
7. **변경 범위** — 문서: §7.3/§8(GIT_COMMIT 세부 기록), §19. DEPLOY 강화를 선택하면: `qms_audit.py`에 deploy-manifest-authorize류 신규 함수 + pre-deploy hook(현재 없음, 신규 설계 필요) + 관련 테스트 — 이건 이 문서의 스코프(조사·계획) 밖이라 별도 작업으로 분리 권장.

### TBD-0008 — Merge 구현 알고리즘·필드 비교 정밀도
